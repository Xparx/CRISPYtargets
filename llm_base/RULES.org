#+TITLE: Rules: CRISPYtargets

* Python Coding Standards

These rules apply to all Python code produced in the project.

** No Nested Definitions

Classes and functions must be defined at the module level. Local
definitions (functions or classes inside other functions/classes)
are forbidden unless they are strictly required for a closure or
a specific decorator pattern.

** Import Discipline

- *Global Imports*: Preferred for all standard dependencies.
- *Local Imports*: Permitted only to avoid circular dependencies
  or to optimize startup time for heavy libraries. Local imports
  MUST be placed at the very top of the function, immediately
  following the docstring.
- *No Interlaced Imports*: Imports must never appear in the
  middle of a logic block.

** Local Function Ordering

If a local function is absolutely necessary, it must be defined
after local imports and before the main execution logic of the
parent function.

** Explicit State

Avoid using closures to maintain state (e.g., defining a list
outside a local class to capture metrics). Use explicit class
attributes or return values.

** AI Coding Discipline

- *Read Before Write*: Request and read full file contents before
  changing anything. Trace data flow end-to-end. Never guess at
  file contents or assume variable types from context.
- *Minimal Change*: Ask "What is the smallest edit that solves
  this problem?" Do not add features, refactor, or optimize
  unless explicitly asked.
- *Match Conventions*: Study how the codebase already handles
  a pattern before introducing a new one. If the pipeline scores
  a metric internally, do not add a parallel implementation.
- *Reuse Before Rewrite*: When existing machinery already
  supports the required behavior, the fix is configuration or
  contract restoration, not a new code path. A parameter being
  ignored is a bug in its contract to fix, never grounds to
  bypass the parameter.
- *Prefer removing bloat over adding flags*: Before proposing a
  new mode or option, check whether an existing one covers it.
  A retired experiment does not become a production flag.
- *No Dead or Redundant Code*: Every line must serve a purpose.
  No padding comments, no obvious comments, no stub functions.
- *Audit All Call Sites*: When fixing a bug or changing a
  pattern, check every file that uses the same pattern. Do not
  fix one instance and leave identical bugs elsewhere.
- *Propose Reasoning Before Code*: State what needs to change
  and why. Confirm the approach before writing any diff.
- *Correctness Over Completeness*: A correct minimal solution
  beats an incomplete ambitious one.

** Data Integrity

- *Data Flow Integrity*: When working with data passing through
  multiple steps (load, transform, compute, save), verify at each
  boundary that the expected format is maintained. Never save
  computed/normalized data into a field that should hold raw data.
  Verify that no redundant transformations are introduced at any
  stage.
- *Data Cost Minimization*: Do not densify sparse data at any
  point unless it is absolutely required.

* Root and User Installs Need Strict Permission

Never create or install Python packages in the root or user space
(system site-packages, =~/.local=, =sudo pip=, =pip install --user=)
without strict, explicit permission for that install. Default work
runs in a virtual or project-local environment; any install that
would reach a shared environment is requested first, with the
target stated.

* Process Concurrency Bound

These rules cap how much work a session fans out at once. Tool
calls count as jobs: file reads, shell commands, and find, grep,
or glob searches are limited the same way spawned processes are.

** The Bound

Never launch more than 10 jobs in one go. A job is any tool call
or spawned process: a file read, a shell command, a find, grep,
or glob search, a parallel tool call, a background job. When in
doubt, it counts.

** Wait Before Starting More

When the bound is reached, wait for every in-flight job to
finish before starting the next batch. Never accumulate
background jobs, queued reads, or extra shells as a substitute
for waiting.

** Search Once, Read What It Points To

Locate before you read: one search over the full scope (one
recursive grep, one glob) instead of many narrow finds or
per-file probes. Read only files the search points at, and never
re-read a file already in context.

** Fan Out Through Bounded Tools

Work past the bound runs through one bounded mechanism
(=xargs -P=, =make -j=, GNU parallel) with its own parallelism
capped at 10, never one tool call or process per job.

* Data Format Rules

These rules govern file formats used when saving tabular data.

** TSV Over CSV

Data table files must be saved in TSV (tab-separated values)
format rather than CSV (comma-separated values) in all areas
where TSV does not interfere with other functionality. Tabs
rarely occur inside data values, so TSV avoids the quoting and
escaping problems that affect CSV text fields.

- *Default*: Any new save, export, or write step that produces
  tabular data uses =.tsv= with tab delimiters.
- *Exception*: CSV is permitted only when a downstream consumer
  requires it (external tool, library API, or fixed published
  format).
- *No Mixed Formats*: The same dataset must not exist in both
  TSV and CSV representations within a pipeline. When converting
  an existing CSV output to TSV, convert all writers and readers
  of that dataset.

* Output Formatting Rules

These rules define how responses should be structured when
intended for copy-paste use or technical writing.

** Strict Inline Math

When writing LaTeX or text containing mathematical symbols,
variables, or equations that are not in a standalone
=\begin{equation}= block, never use the dollar sign =$= for
framing. Use =\( ... \)= for all inline mathematical
expressions.

** M-dash

Never use m-dash in running text. Reword the sentence or use a
comma instead.

** Response Structure

Foundational: minimal technical bullshit, clean and concise
information. This applies to every reply, not only large-scope
ones.

- Lead with the answer, status, or next step.
- Provide only the technical detail necessary to understand the
  point and act on it. Mechanics (file lists, staging detail,
  tool narration) stay out unless they change a decision.
- Everything else waits until the user asks. Detail is always
  available on request, so never front-load it.

** Follow Rules, Do Not Recite Them

Rules are followed, not quoted. Never regurgitate, cite, or hint
at rules in responses: no "per RULES.org", no summaries of the
rules being applied, no reminders about them. The user sees the
result of the rules, not the rules themselves. Explain reasoning
when asked, but never preemptively advertise which rule drove a
decision.

** Copy Blocks (Locate and Replace)

When providing text for the user to paste into a file:

- Metadata (file, location, anchor) goes in plain text outside
  the fences; each fenced block holds only the lines that land
  in the file.
- Precede the paste block with the exact line it follows, or
  the exact lines it replaces, so the spot is findable with a
  text search.
- Blocks contain whole lines only, wrapped to the target file's
  line width.
- End every block with an extra empty line: the pasted text
  must carry its own trailing newline so it never merges with
  the line that follows it in the file.

* Document Integrity Rules

These rules protect document metadata during refactoring and
editing tasks.

** Citation Preservation

The removal or modification of citations (e.g., =\cite{...}=)
is strictly forbidden unless explicitly requested by the user.
Citations are considered critical document metadata; their
removal is a destructive action and must be avoided during all
text refactoring or alignment tasks. The same applies to the
DOI and citation lists in =README.md=.

* Research Integrity Rules

These rules govern how computed numbers are produced, cited, and
made reproducible in projects that report quantitative results.

** Authoritative Computation

Never hand-compute statistics. Numbers cited anywhere (manuscript,
docs) must come from a script reading the raw output files; the
document is corrected to match the computation, never the reverse.
No hardcoded claimed values for validation. Scores reported from
the pipeline (Doench 2016, Rule Set 3, FlashFry metrics) must come
from run outputs, not from notes.

** Provenance Anchoring

Every published number must trace to an artifact bundle recording
the code version (git commit or package version) and checksums of
the input data. No number without a bundle.

* Instruction File Stability

AI instruction files are written once during project setup and then
remain fixed. They define how sessions behave; sessions must not
rewrite the definitions they operate under.

** Covered Files

Setup-written files that instruct or configure AI sessions:

- =AGENTS.md= — opencode session startup
- =RULES.org= — consolidated rules
- =roles.org= — AI role definitions
- =opencode.jsonc= — permissions and session configuration
- =.opencode/commands/commitmsg.md= — pre-existing command file

The class is "files that tell AI sessions how to behave".

** The Rule

- *Setup Is Exempt*: Filling placeholders and writing these files
  during scaffolding is expected work, not a violation.
- *Fixed After Setup*: Afterwards a session never edits these files
  on its own initiative — no "improvements", no appending rules it
  discovered, no fixing gaps it perceives.
- *Explicit Request Only*: Changes happen only when the user
  explicitly asks, and only when a specific, persistent problem
  warrants the update — not for convenience or style.
- *Report, Don't Fix*: A session that believes an instruction file
  needs changing states the case to the user and waits.
- *Commands, Split Rule*: Pre-existing files in =.opencode/commands/=
  are fixed like the rest. Creating a NEW command file is allowed when
  the work needs one — extending tooling is not rewriting the rules
  the session runs under.

** Mechanical Enforcement

For opencode projects, =opencode.jsonc= carries matching permission
rules that deny the edit/write/patch tools for these files. Existing
commands are listed by exact path rather than a wildcard, so new
command files remain creatable — when you add a command, add its
deny line too. The block is a backstop, not a replacement: it does
not cover shell commands.
The behavioral rule above remains binding everywhere.

** Rationale

These files hold the constraints the session itself must follow.
A session editing them is grading its own homework: it can silently
weaken any rule it is subject to. Stability of the instruction layer
is what makes the other rules trustworthy.

* Simplicity Principle

Choices must favour simple solutions over complex ones whenever
both meet the need. Prefer the straightforward approach, fewer
moving parts, and standard tools over custom machinery;
complexity must earn its keep with a concrete reason. Reviews
treat simplicity as a primary aim: complexity without
justification is flagged, and the simpler alternative is
proposed before the change is accepted.

* Dependency Bounds

- No upper bounds: version pins in packaging metadata must not
  cap the top of a range (e.g. =numpy<2=) unless no other option
  can be found
- Accidental package downgrades are forbidden: an install or
  update must never silently reduce a version already present
  in the environment; check what an install would change
  before running it
- A downgrade happens only when it is explicit and reviewed:
  a deliberate decision to add the older version to the stack,
  with the reason stated before the install runs

* Commit Messages

How commit messages are written and when commits are made.

** Message Format

- Subject line: imperative mood, one line, with a type prefix
  where it fits (=docs:=, =feat:=, =fix:=, =chore:=).
- Blank line, then body bullets describing what changed and why;
  one bullet per file or concern.
- Keep the subject readable in =git log --oneline=.
- Trivial changes may be subject-only, but never skip the
  trailer.

** The Co-Authored-By Trailer

Every commit ends with the trailer as its final line:

=Co-Authored-By: <your model ID>=

- Blank line between the last body line and the trailer.
- Single line; the key is exactly =Co-Authored-By=.
- The model states its own model ID as the value. If the ID is
  unknown, say so when presenting the draft instead of guessing.

** When Commits Happen

- Commits are a separate, explicitly requested step: finish the
  changes, present the draft message, and commit only when the
  user says go. Never bundle a commit into another task.
- Long-running jobs may carry a standing "commit as you go"
  authorization; each message is still recorded and reported at
  the end.
- Reserved files (=AGENTS.md=, =RULES.org=, =roles.org=,
  =opencode.jsonc=, =.opencode/commands/=) need
  explicit per-commit go even under a standing authorization.

** Branch Alignment

- Never rebase, merge, fast-forward, reset, or otherwise move a
  branch relative to main/master (or any shared branch) without
  asking the user first.
- Aggregating, squashing, or reordering commits is a history
  rewrite: check whether the branch has diverged from
  main/master, flag that a rebase or merge against main may
  happen first, and ask which way to proceed before touching
  anything.
- Never rewrite commits already pushed to a shared branch
  without asking.

* File and Directory Placement

Where a file lives is a decision, not a reflex. These rules govern
new work: what gets created, where it goes, and what is left alone.

** 1. Placement Is a Decision

Before creating a file or directory, find where its kind already
lives and extend that. A new path is justified only when no
existing home fits its purpose.

** 2. No Sprawl

- No new top-level directory without asking first.
- No directory created to hold a single file.
- No catch-all directories: `junk/`, `old/`, `new/`, `misc/`,
  `backup/`, `deprecated/`, `temp_*`, `test2`, dated folders.
- The project root holds project files, session files, config,
  and deliberate domain directories. It is not a workbench and
  not a shelf.
- Scratch work is explicit: a named, ignorable location, cleaned
  or deliberately left untracked. Never silently committed.

** 3. Derive from Precedent

Existing structure governs. If the project already keeps figures
in one directory, new figures go there; do not open a parallel
`figs_v2/` because the name is disliked. Preference never
overrides precedent.

When no precedent exists, derive the location from need: who
writes the file, who reads it, how long it lives, whether it can
be regenerated. Choose the least surprising option and keep it
consistent afterwards.

** 4. The Repository Is Not the Working Directory

For compute and method development, the repository holds code,
configuration, small fixtures, and the record of what was run.
It does not hold the working set.

- Datasets, model checkpoints, embeddings, benchmark outputs,
  sequencing archives, and large intermediates live in a work
  area outside the repository.
- `.gitignore` is a safety net, not a licence. An ignored
  multi-gigabyte checkpoint is still sprawl in the tree.
- Results that belong in the project are the small, final
  artifacts the project actually needs, plus their provenance.

** 5. Work Areas Come from Local Precedent

Where bulk data lives is decided inside each project, never
prescribed from outside and never invented on the spot.

- Follow the project's existing convention when one exists.
- Where none exists, and the data_bibliography source project is
  available, consult it for this machine's data and cluster
  conventions.
- Local precedent outranks that source: if the project already
  answers the question, the project's answer wins.
- Record the chosen location once, in the project's own files,
  so the next session does not have to decide again.

** 6. Existing Paths Are Not to Be Moved

These rules govern where new work goes. They are not a mandate
to reorganize.

- Nothing pre-existing is relocated, renamed, consolidated, or
  cleaned up until the user requests that specific move as its
  own task.
- Agreeing with a rule is not permission to enforce it
  retroactively. A messy directory that already exists is not
  evidence of disorder to fix; it is the current convention
  until the user says otherwise.
- Harmonization happens over time, inside work that already
  touches those files. The rule shapes what is added from now
  on.

** 7. Moves Update All References

A relocation is complete only when nothing points at the old
path. Update every reference in the same change: configuration,
documentation, scripts, links, and instruction files.

** 8. Symlinks Are Deliberate Patterns

A symlink is acceptable when it is a documented, repeatable
structure, such as a shared framework mounted into a project. It
is not acceptable as a patch over a misplaced copy, a shortcut
around deciding where something belongs, or a way to reference
content that should have been copied.
